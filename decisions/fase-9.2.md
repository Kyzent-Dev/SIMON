## Fase 9.2, Task 6
- `PerubahanPkpt::cek()` rules, in order: PKPT Disahkan (`Perubahan hanya untuk PKPT yang sudah disahkan.`); at least one operasi (`Tambahkan minimal satu operasi.`); per operasi, prefixed `Operasi {urutan} ({aksi} · {jenis} · {irban})` (jenis/irban from `data_baru` for tambah, from the item otherwise): item of this PKPT and `aktif` (ubah/hapus); `hapus` of an item with any SPT → K7; `SavePkptItem::validated` messages (tambah/ubah); `ubah` changing irban/jenis of an item with any SPT → K7; `ubah` equal to the item → `Tidak ada yang berubah.`; the same item in two operasi → `Item ini sudah ada di operasi lain pada perubahan ini.`. The per-operasi rules live in `PerubahanPkpt::galat()`, which `SimpanOperasi` throws (keyed by field) so the messages match `cek()`.
- Item added by a paket: snapshot `tanggal_*_disahkan` = its own dates at approval, so it is never "direvisi" until a later paket moves it.
- `PenerimaNotifikasi::pembuatPerubahan`: the creator when that account still exists and is Admin, else every Admin. `perubahanDisetujui` uses it for the creator part, adds every Pimpinan and the Irban accounts of every irban touched (data_baru, data_lama, item irban; `PerubahanPkpt::irbanTerdampak`, also used by the policy), minus the decider.
- Reminders: per paket at most one per Jakarta day (`pengingat_terakhir_pada < today 00:00`); the first one comes the day after submission (`diajukan_pada < today`) for Pimpinan, and the day after approval (`diputuskan_pada < today`) for the Admin SK reminder (only `sumber = admin`, `sk_lengkap_pada` null, not dimatikan). The info line of `notifikasi:harian` gained both counts (`NotifikasiHarianMingguanTest` expectation updated).
- SK file: private `local` disk, `perubahan-pkpt/{id}/{uuid}.pdf`, `hash_sk` SHA-256, same PDF rules and limit as SPT documents (`BerkasSpt::pdf`, `upload.maks_mb`). Blank nomor/tanggal clear the field, no file keeps the current one; nothing changed → no riwayat row. `sk_lengkap_pada` keeps the first completion time while complete, null otherwise. Download route returns 404 when `berkas_sk` is null or the file is missing, 403 when `unduhSk` is denied; the name is `sk-perubahan-pkpt-{tahun}[-ke-{N}].pdf`.
- Re-submitting a ditolak paket keeps `komentar_putusan` of the rejection (also in the riwayat `ditolak` row); a later decision overwrites it with its own komentar (null when approving without one).
- Notification URLs `admin.pkpt.perubahan` and `pimpinan.perubahan-pkpt.show` do not exist until Tasks 7/8, and `route()` would throw: the notifications build the E7 paths literally (marked `shortcut:`); Tasks 7/8 should switch them to `route()`. `PerubahanPkptDiputuskan` picks the URL per recipient role (Admin paket page, Pimpinan detail, Irban `irban.pkpt`).
- Notification payload properties avoid the name `$id` (the framework `Notification::$id` is public; redeclaring it crashes PHP).
- The concurrency harness of `PenomoranKonkurensiTest` moved unchanged into the trait `Tests\Support\KonkurensiProses` (script path now an argument of `jalankan()`), shared with `PerubahanPkptKonkurensiTest` and its child script `tests/Support/putuskan-perubahan.php`. Both ran green on local MariaDB 10.4 (XAMPP).
- `BuatPerubahan::perbarui` writes no riwayat row (E4 has no kejadian for it). `AturPengingatSk` is a no-op without riwayat when the reminder is already in the requested state.
- Fix round 1: lock order for PKPT items is always `pkpt` row first, then everything else. `PutuskanPerubahan` locks `pkpt` then the paket; `SimpanSpt` (when the SPT has a `pkpt_item_id`) now locks the item's `pkpt` row with `lockForUpdate()` at the start of its transaction, before the SPT row and `Penomoran`, and re-reads the item (`aktif()`, own irban, same jenis) under that lock, rejecting with the existing `Item PKPT tidak valid untuk Irban ini.` message. So an approval that removes the item or changes its irban/jenis cannot commit in the same window as a new SPT on it, which keeps the Task 5 assumption that no SPT points to a dihapus item. Saves without an item take no PKPT lock.
- Fix round 1: `SimpanOperasi` reports a missing, out-of-scope or dihapus item with `PerubahanPkpt::ITEM_TIDAK_ADA` (the `cek()` message), not `Pilih item.`. `PutuskanPerubahan` validates the komentar after the status check, so a stale tab gets `Perubahan ini sudah diputuskan.` first.
